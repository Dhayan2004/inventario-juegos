## Workflow

### Paso 1: Verificar Brand DNA + Cargar Tokens

Ya pasaste el R10 gate (arriba). Ahora cargar el contrato:

```
brand_json = Read brand/brand.json
voice_json = Read brand/voice.json
component_rules = brand_json.component_rules (si existe — output de impeccable BATCH previo)
```

Estos son contrato **no-negociable** (R10):
- `brand_json.tokens.colors` — usar verbatim, NO Tailwind defaults.
- `brand_json.tokens.typography` — fuentes y escalas declaradas.
- `brand_json.tokens.radius` / `spacing` / `shadows` — coherencia producto-wide.
- `brand_json.archetype` + `posture` — guía estética (Sage / Creator / posture density+expression).
- `voice_json.tone` + `cta_examples` + `microcopy` — copy derivado.
- `brand_json.anti_slop` rules — colors blacklisted, hue range prohibido.

### Paso 2: Identificar Componentes Necesarios

Para cada screen flow del asset 07:

1. Lista de componentes requeridos (Button, Input, Card, Modal, Form, Table, etc.).
2. Cross-reference con `component_rules` de brand.json:
   - Si componente está declarado → usar `impeccable` Mode KNOWN.
   - Si componente NO está declarado → usar `impeccable` Mode UNKNOWN (derivación R-005 sec 8.2).
3. Si es la PRIMERA pasada del proyecto → invocar `impeccable` Mode BATCH para generar core component set (Button, Input, Card, Modal, Form, Tabs, Sidebar, Topbar, Breadcrumb, Select, Textarea — los 11 canónicos).

### Paso 3: Implementar Screen por Screen

Orden recomendado:
```
1. Layout shell + navegación (asset 06 IA — establece look & feel global)
2. Pantalla principal / Dashboard (la más compleja, define el sistema)
3. Formulario principal (asset 06 interaction-patterns: validation, R14 destructive)
4. Empty states (asset 06 onboarding.md — first success flow)
5. Vistas de listado / tabla
6. Vistas de detalle con state transitions
7. Pantallas de auth (delegar a `/add-login` template — D-009)
8. Pantallas secundarias (settings, perfil, etc.)
```

Para cada pantalla:

1. Leer screen flow (layout, data, actions, states, acceptance targets).
2. Revisar interaction patterns del asset 06.
3. Dispatch sub-agent con skill `impeccable`:
   - Contexto: brand_json + voice_json + screen flow + acceptance targets + interaction patterns + IA pattern.
   - Output: `src/features/[feature]/[Screen].tsx` (Feature-First).
4. Cubrir TODOS los estados: Default, Loading, Empty (según onboarding.md), Error, Success.
5. Anti-Slop Gate (`impeccable` lo aplica internamente):
   - Brand Score ≥75.
   - Tokens compliance verbatim.
   - No colors blacklisted, no hue range prohibido.

### Paso 4: Componentes Nuevos (Mode UNKNOWN)

Para componentes nuevos identificados en asset 07 que NO están en `component_rules`:

1. Dispatch sub-agent con `impeccable` Mode UNKNOWN.
2. Contexto: spec del componente (asset 07) + brand_json + voice_json + nearest_component (de los 11 canónicos).
3. Output: `src/shared/ui/[ComponentName].tsx`.
4. el-evaluador puede promover el componente a `component_rules.json` si reusable cross-feature.

**Reglas de implementación de componentes:**
- Tipado TypeScript completo.
- Variantes con CVA (class-variance-authority) si hay múltiples variantes.
- Accesibilidad: role, aria-label, keyboard navigation, contraste WCAG AA.
- Estados: default, hover, focus, disabled, error, loading.

### Paso 5: Anti-AI-Slop Check

`impeccable` lo aplica automáticamente, pero para validación final:

```
✅ ¿Si pongo 10 apps generadas por IA en una fila, esta se distingue? → SÍ
✅ ¿La tipografía tiene personalidad? → No es Inter/Roboto/Arial defaults
✅ ¿La paleta tiene DOMINANCIA? → Un color manda, no equidistantes
✅ ¿Cards, botones, inputs tienen identidad PROPIA? → Tokens de brand.json verbatim
✅ ¿Hay al menos UN detalle memorable? → [identificarlo]
✅ ¿Estados empty y error fueron diseñados? → No placeholders genéricos
✅ ¿Motion tiene intención? → No bounces arbitrarios
✅ ¿Navegación refleja el patrón del asset 06? → Coherencia con IA
✅ ¿Interaction patterns del asset 06 implementados? → Comportamiento consistente
✅ ¿Empty states guían al first success? → Según onboarding.md
✅ ¿Brand Score ≥75 reportado por impeccable? → SÍ
```

Si algún check falla → corregir antes de entregar.

## Reglas Críticas

- **R10 strict — sin Brand DNA, halt.** No hay excepción.
- **`impeccable` es el ejecutor, no el orchestrator.** Este asset coordina; `impeccable` genera componentes.
- **Tokens de brand.json verbatim.** Nunca Tailwind defaults para colors/typography/spacing.
- **Implementar TODOS los estados.** Empty (onboarding.md), error (interaction-patterns.md), loading.
- **Acceptance targets del asset 07 son requisitos.** Sin cumplir = pantalla incompleta.
- **Dispositivo primario lo definen las personas del asset 04.**
- **Patrón de navegación lo definió el asset 06.** No cambiarlo ni mezclarlo.
- **Interaction patterns del asset 06 son producto-wide.**
- **R14 strict en destructivas:** delete account, cancel subscription, send bulk, etc. — typed confirmation, no `execute()` automático.
- **R13 citation grammar:** [docs:nextjs], [docs:shadcn-ui], [docs:tailwindcss] cuando se cite sintaxis.
- **Alcance conceptual independiente de prefijo (E-009 causa 2):** las rutas mencionadas (`src/...`, `brand/...`, `src/shared/ui/...`) son patrones, NO literales. La restricción "no tocar archivos críticos del proyecto sin Brand DNA contract" aplica con o sin prefijo ``. Cualquier `**/src/app/globals.css`, `**/tailwind.config.*`, o `**/src/app/layout.tsx` con contenido propio → halt o handoff a add-ui-kit. Cita [memory:errors#E-009].
